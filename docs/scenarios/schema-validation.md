# Scenario 34 — Structured data at site scale: valid, eligible, and neither

## The question

> Run the markup across the whole site. I want to know which pages are broken, which are merely
> incomplete, and which have nothing at all — as three lists, not one score.

Three lists, because they are three jobs. A block that will not parse is a developer bug. A
valid block missing a required property is a content gap. A page with no markup is a decision
nobody made.

The [structured data scenario](structured-data.md) diagnoses one page in depth. This one triages a site.

## Covers

- **Structured Data** — Validation Errors · Rich Result Validation Errors · Parse Errors · Missing · Validation Warnings · Rich Result Validation Warnings

## The chain

**1. Crawl, and read the two block counts.** Every page records `jsonld_blocks_found` against
`jsonld_blocks_parsed`.

```bash
seohead crawl-site --url https://example.com --out-dir ./run --max-urls 200
```

"Found 3, parsed 2" is a **parse error**: one block is malformed. Both numbers are kept for
exactly this reason — reporting that page as having no structured data would describe a
different page. Note the honest limit: the counts make a malformed block *visible*, but a parse
error is not raised as its own registry finding, so it has to be read rather than filtered.

```bash
seohead log-scan --run ./run
```

**2. Get `STRUCTURED_DATA_MISSING` and `SCHEMA_VALIDATION_ERROR` at site scale.** Both come from
a Screaming Frog export: the first from the `Structured Data:Missing` filter, the second from
the validation columns in `Internal:All`.

```bash
seohead sf run --exports-dir ./exports --out report --tasks
```

When those columns are absent, the checks name themselves skipped — `no Structured Data
validation columns in Internal:All`, `missing export: structured_data_missing` — rather than
reporting a clean site.

**3. Separate validity from eligibility on the pages that matter.** These are different
questions and they fail for different reasons, so they are reported separately.

```bash
seohead schema-check --url https://example.com/page
```

- **Vocabulary validation** — is this a real Schema.org type, are these real properties, is
  anything deprecated. Errors and warnings are attached per entity, with the path they were found
  at, so `brand` and `offers` are named rather than "the markup".
- **Rich-result validation** — does Google's requirement list for this type have what it needs.
  `missing_required` is an error: the page is not eligible. `missing_recommended` is a warning:
  it is eligible and weaker.
- **Graph shape** — `is_graph`, and the `islands` list of entities linked by nothing.

**4. Generate what is missing rather than describing it.**

```bash
seohead schema-build --url https://example.com/page --type Product
```

It reads the page and builds the connected `@graph` — `Organization`, `WebSite`, `WebPage`, then
the page's own type — instead of asking you to write one. Pass `--type` only when the
classifier's confidence is low.

**5. Ship the three lists.**

```bash
seohead sf tasks --json ./report/audit.json --out ./report
```

## What comes out

The two layers, side by side, from one page:

```json
{
  "blocks_found": 1,
  "blocks_invalid": 0,
  "graph": {"nodes": 3, "with_id": 1, "linked_by_id": 0, "is_graph": false},
  "entities": [{"path": "offers", "types": ["Offer"], "errors": [], "warnings": []}],
  "rich_results": [
    {"type": "Product", "eligible": true, "missing_required": [],
     "missing_recommended": ["image", "aggregateRating", "review"]}
  ],
  "findings": [
    "3 entities are marked up, but none are linked through @id; this is a set of isolated blocks rather than a graph"
  ]
}
```

That last finding is the common one. A disconnected top-level graph — `linked_by_id: 0` — is a
local structural finding worth reviewing; it does not explain whether Google will show a rich
result. Fixing the isolation with `@id` references is still worth doing, but do it as
remediation of a structural finding, not as the diagnosis for a missing SERP feature.

## What it costs

One request per page for the crawl, one per page for `schema-check` and `schema-build`. No
Google API is involved and nothing is paid. Run `schema-check` on one page per template first;
markup is generated by a template and repeats its mistakes exactly.

## What it cannot answer

- **Whether Google will show a rich result.** Eligibility is necessary, not sufficient. Google
  decides, and quality and trust signals nobody can read are part of it.
- **Whether the data is true.** Nothing verifies a declared price, address or rating. Markup that
  contradicts the visible page is a manual-action risk this cannot see.
- **Parse errors as a filterable finding.** They are visible in the found/parsed counts and in
  `parse_errors`, and they are not raised as their own registry check.
- **Site-scale validation without an export.** A native crawl records the block counts; the
  validation columns and the missing-markup filter come from Screaming Frog.
- **Markup injected after load.** See the [rendering scenario](rendering.md).
