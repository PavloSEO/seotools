- The native crawler's rendering step now exposes its browser through configuration instead
  of hard-coding Chromium: `rendering.browser.engine` selects `chromium` (still the default),
  `firefox` or `webkit` through the same guarded Playwright path, an unknown name fails during
  settings validation rather than at launch, and a requested engine whose binary is not
  installed reports a dependency error that names the fix (`playwright install <engine>`)
  instead of silently falling back to Chromium. Firefox's documented limitation is enforced
  honestly: it rejects `rendering.browser.mobile_emulation` (`is_mobile` is unsupported there)
  while the independent `rendering.browser.touch_emulation` (`has_touch`) still reaches the
  context. Probes and full renders share one effective configuration, so a pattern is never
  escalated by a browser that differs from the one producing its evidence.
- `rendering.browser.viewport_width` and `rendering.browser.viewport_height` add arbitrary
  viewport dimensions alongside the existing `desktop`/`mobile` presets, which keep deciding
  the profile exactly as before. The pair is all-or-nothing and bounded to 1..16384 px; a
  custom pair replaces the preset's dimensions only -- it does not imply mobile or touch
  emulation, which remain explicit flags an operator states.
- `rendering.browser.page_concurrency` bounds how many browser fetches may be in flight
  during escalation, separately from `speed.concurrency`, which keeps governing HTTP crawl
  politeness. The default of 1 preserves the sequential behaviour and builds no pool at all;
  above 1, probes and renders run on a bounded worker pool while every verdict, commit and
  SQLite write stays on the orchestrator thread in submission order. The render deadline,
  URL budget and sampled/full policies hold under concurrency, a stopped batch waits out the
  pages it already started and never schedules new ones, and interrupted or failed workers
  leave no thread, page, context or browser alive behind the call.
- The selected engine, its actual reported version, the effective viewport and the configured
  page concurrency are recorded in the crawl manifest and fingerprint and in every rendered
  document's renderer provenance -- including failed attempts, which record what was requested
  without inventing a successful render. Both escalation paths honour the settings: the
  directory crawl and the native SQLite scan, where rendered-link candidates still enter the
  frontier through the existing deduplicating admission once `rendering.rendered_links.crawl`
  is enabled.
