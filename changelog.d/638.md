- Move changelog entries out of `CHANGELOG.md` and into one file per change under
  `changelog.d/`, so a pull request no longer conflicts with every other pull request that
  landed before it (#638). Every branch added its entry at the top of `## Unreleased`, which
  made that one line the file's contention point: nine hand-resolutions across eight pull
  requests in two sessions, each a re-push and a fresh CI run, and the resolution was "keep our
  block, then theirs" every single time. A conflict whose answer never varies carries no
  information and is a chance to drop a paragraph while thinking about something else. The
  `.gitattributes` fix the issue proposed -- `CHANGELOG.md merge=union` -- was measured and
  rejected before this: union merges line by line, so when both entries contain an identical
  line (a blank line inside an entry is enough) it keeps one copy and reports success, deleting
  the other entry's line with no conflict and nobody prompted to look. A first test with
  deliberately distinct lines merged cleanly and hid that. Trading a loud conflict for silent
  data loss is strictly worse than the conflict, so the structural fix is the one that shipped.
- A fragment is named for the issue it closes (`changelog.d/638.md`), the key that is unique to
  a branch by construction: one pull request closing two issues writes two fragments, one per
  issue, and a change that closes nothing writes `no-issue-<slug>.md`. A fragment holds the
  entry exactly as it belongs in the changelog -- one or more top-level bullets with their
  continuation lines, no front matter and no wrapper -- so the multi-paragraph prose entries
  this file carries round-trip byte for byte rather than being reformatted into one-liners.
  `python scripts/build_changelog.py` folds them into `## Unreleased` at release time, ordered
  by issue number rather than by whatever order the filesystem hands back, and `--prune`
  removes the fragments it folded in. Assembly replaces the whole region between two marker
  comments instead of inserting into it, so running it twice produces the same file both times
  whether or not the fragments were pruned in between. `CHANGELOG.md` itself is not regenerated
  on every pull request, deliberately: a gate that kept it continuously in sync would put both
  branches back in the same file and rebuild the conflict this removes.
- The doc gates that read `CHANGELOG.md` were the risk, because a gate that quietly stops
  checking anything is worse than the conflicts. Both were found and both now cover the
  fragments: `tests/test_docs_drift.py` carried `CHANGELOG.md` in `PUBLIC_MARKDOWN`, so the
  English-only gate, the "references only existing commands" gate and the stale-count gate now
  read `changelog.d/*.md` as well, and the two count-drift gates skip a fragment for the same
  reason they skip the changelog -- an entry records what was true when it was written.
  `tests/test_doc_counts.py` deliberately excludes the changelog from its live-count scan and
  its file list never reaches `changelog.d/`, which is the same answer for the same reason;
  `tests/test_doc_commands.py`, `tests/test_docs_commands_execute.py` and
  `tests/test_examples_gate.py` never read the changelog at all. A new
  `tests/test_changelog_fragments.py` pins each of those answers, along with fragment naming,
  deterministic order, idempotent assembly, and the fact that two simulated concurrent branches
  adding a fragment each merge without a conflict.
